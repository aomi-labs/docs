Aomi exposes separate Model Context Protocol resources for stateful Agent work and direct Pipeline operations. Connect Codex, Claude Code, Cursor, or another Streamable HTTP MCP client.

## Choose a resource

| Resource | Use it for | Path |
| --- | --- | --- |
| Agent MCP | Start and resume conversations, watch progress, and hand actions to a human. | `/v1/agent/mcp` |
| Pipeline MCP | Discover Apps and tools, inspect schemas, and call admitted operations directly. | `/v1/pipeline/mcp` |

Use Agent MCP for conversational work. Use Pipeline MCP when your MCP client needs explicit catalog and operation control.

<Warning>
  `/api/mcp` and `/api/mcp/direct` are removed and return `404` on staging. Use the exact Agent or Pipeline resource.
</Warning>

## Endpoints

| Environment | Agent MCP | Pipeline MCP |
| --- | --- | --- |
| Staging | `https://chat-staging.aomi.dev/v1/agent/mcp` | `https://chat-staging.aomi.dev/v1/pipeline/mcp` |
| Production | `https://chat.aomi.dev/v1/agent/mcp` | `https://chat.aomi.dev/v1/pipeline/mcp` |

<Note>
  Confirm that the `/v1` resources are enabled in your target environment before production rollout. Staging and production have separate accounts, grants, and conversations.
</Note>

## Connect Agent MCP

<Tabs>
  <Tab title="Codex">
    ```bash
    codex mcp add aomi-agent --url https://chat-staging.aomi.dev/v1/agent/mcp
    codex mcp login aomi-agent
    ```
  </Tab>
  <Tab title="Claude Code">
    ```bash
    claude mcp add --transport http aomi-agent \
      https://chat-staging.aomi.dev/v1/agent/mcp
    ```

    Run `/mcp`, select **aomi-agent**, and authenticate if the browser flow does not start automatically.
  </Tab>
  <Tab title="Cursor">

    ```json
        "aomi-agent": {

    ```
  </Tab>

  </Tab>

## Agent tools

| Tool | What it does |
| --- | --- |
| `aomi_chat` | Start or continue an Agent turn. |
| `aomi_check` | Read new messages and activity using an opaque progress cursor. |
| `aomi_interrupt` | Stop the active turn in a session. |
| `aomi_list_sessions` | Find recent conversations owned by the authenticated account. |

### Supervise a turn

<Steps>
  <Step title="Start the turn">
    Call `aomi_chat`. Omit the session ID for a new conversation or use one returned by `aomi_list_sessions`.
  </Step>
  <Step title="Keep the cursor">
    Pass the returned cursor to `aomi_check` without editing it.
  </Step>
  <Step title="Poll for progress">
    Continue while the status reports processing. Stop at a terminal status or when Aomi needs user input.
  </Step>
  <Step title="Hand actions to the user">
    When a response includes a pending action, send the user to the Aomi portal or an authenticated CLI. Call `aomi_check` again after approval or rejection.
  </Step>
</Steps>

Do not report transaction success until a later check returns the confirmed result.

## Connect Pipeline MCP

```bash
codex mcp add aomi-pipeline \
  --url https://chat-staging.aomi.dev/v1/pipeline/mcp
codex mcp login aomi-pipeline
```

Pipeline MCP supports a broad-to-narrow workflow:

1. Read Agent context when an operation needs it.
2. List Apps and namespaces.
3. List the tools in the selected namespace and inspect their schemas.
4. Call one tool with validated arguments.

The current Pipeline MCP routes expose `aomi_get_agent_context`, `aomi_list_apps`, `aomi_list_namespaces`, `aomi_list_tools`, and `aomi_call_tool`. The live inventory can evolve with the deployed resource, so use the client's tool-list response as the final authority.

## Authentication and signing

The first unauthenticated request receives an OAuth challenge. Your MCP client uses PKCE and requests a token for the exact MCP resource.

Agent and Pipeline grants are separate. Signing authority is separate again:

- OAuth identifies the Aomi account and authorizes the MCP operation.
- A linked wallet makes an address available to account-owned work.
- Each action still follows the wallet's review and signing policy.
- Private keys, seed phrases, and reusable signatures do not pass through MCP.

<Warning>
  Authorize only MCP clients you trust. An authorized client can act within its granted Agent or Pipeline scopes, even though wallet policy still controls signing.
</Warning>

## Troubleshooting

| Symptom | Check |
| --- | --- |
| `401 Unauthorized` | Complete OAuth for this exact MCP resource. |
| `403 Forbidden` | Do not reuse an Agent token for Pipeline or the reverse. |
| Guest REST token rejected | MCP requires OAuth for its exact `/mcp` resource; a guest REST bearer is not an MCP grant. |
| Browser does not open | Use the MCP client's manual login command and inspect its OAuth status. |
| Session not found | Confirm you authenticated to the environment and account that owns it. |
| Action remains pending | Complete review in the portal or authenticated CLI, then call `aomi_check` again. |

See [Authentication](/integrate/authentication) for the full caller identity model.
