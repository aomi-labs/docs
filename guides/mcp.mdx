Aomi exposes a hosted [Model Context Protocol](https://modelcontextprotocol.io) server. Point a coding agent at it and the agent can search Aomi's tool catalog, read chain state, and execute on-chain actions inside your Aomi account — no CLI install, no local process.

This is the direct-connection counterpart to [Skills](/guides/skills). Skills teach your agent to drive the `aomi` CLI on your machine, with local transaction signing. MCP is a server connection: discovery and execution run on Aomi's backend, inside a thread owned by your account, behind the same skill gates and signing policy as every other Aomi surface.

## Endpoints

| Environment | URL | Transport |
| --- | --- | --- |
| Production | `https://chat.aomi.dev/api/mcp` | Streamable HTTP |
| Staging | `https://chat-staging.aomi.dev/api/mcp` | Streamable HTTP |

The server speaks the stateless subset of MCP streamable HTTP: one JSON-RPC message per POST, JSON responses, no SSE push, no server-issued sessions, no batch requests. Any client that supports streamable HTTP with OAuth works.

<Note>
Staging is a separate account graph. A sign-in or wallet link on production does not carry over to staging, and vice versa.
</Note>

## Connect

<Steps>
  <Step title="Add the server">
    **Claude Code:**

    ```bash
    claude mcp add --transport http aomi https://chat.aomi.dev/api/mcp
    ```

    Or in a project's `.mcp.json`:

    ```json
    {
      "mcpServers": {
        "aomi": {
          "type": "http",
          "url": "https://chat.aomi.dev/api/mcp"
        }
      }
    }
    ```

    **Cursor** — in `.cursor/mcp.json` (project) or `~/.cursor/mcp.json` (global):

    ```json
    {
      "mcpServers": {
        "aomi": {
          "url": "https://chat.aomi.dev/api/mcp"
        }
      }
    }
    ```

    **Any other MCP client:** configure a streamable-HTTP server at the URL above. The server advertises protocol version `2025-06-18` and answers OAuth discovery at `/.well-known/oauth-protected-resource` and `/.well-known/oauth-authorization-server` on the same origin.
  </Step>
  <Step title="Authorize">
    The first request returns `401` with a `WWW-Authenticate` challenge, which triggers your client's OAuth flow: dynamic client registration, PKCE, and a browser hop to `chat.aomi.dev/mcp/connect`. Sign in, then approve the client on the consent screen.

    In Claude Code, run `/mcp`, select **aomi**, and choose **Authenticate** if the flow doesn't start on its own.

    The token identifies your Aomi account. Every tool call executes as you: your linked wallets, your skill entitlements, your threads.
  </Step>
  <Step title="Link a wallet (for execution)">
    Discovery works with a bare account. Execution that touches chain state needs an operating wallet: the backend seeds each MCP call with your account's primary EVM key. If no wallet is linked, staged transactions fail with a connect-first error — link a wallet at [chat.aomi.dev](https://chat.aomi.dev) first.
  </Step>
  <Step title="Verify">
    Ask your agent to call `aomi_get_agent_context`. It returns your MCP thread id, a catalog summary, and the discovery workflow. From there:

    ```text
    aomi_search_apps("swap") → aomi_search_tools("swap usdc") → aomi_describe_tool → aomi_call_tool
    ```
  </Step>
</Steps>

## Tools

The server exposes ten tools in a broad-to-narrow funnel: find the app, find the tool, read its schema, call it.

| Tool | What it does |
| --- | --- |
| `aomi_get_agent_context` | Return the authenticated context: thread id, catalog summary, discovery workflow. |
| `aomi_list_apps` | List compact app candidates. |
| `aomi_search_apps` | Ranked app search by name, namespace, or capability — the fast broad pass. |
| `aomi_search_tools` | Ranked tool search, scoped to one app or global — the fast narrow pass. |
| `aomi_select_app` | Load one app's full instructions and namespace catalog. Returns context; does not set server state. |
| `aomi_list_namespaces` | List an app's capability groups with preview tools. |
| `aomi_list_tools` | List tools for an app, optionally filtered by namespace. |
| `aomi_describe_tool` | One tool's exact input schema plus owning-skill instructions. Call before `aomi_call_tool`. |
| `aomi_call_tool` | Execute a single Aomi tool inside your MCP thread. Skill-owned tools activate their skill automatically. |
| `aomi_run` | Run a multi-step orchestration program — many tool calls in one request, intermediates staying server-side. |

The server is stateless by design: pass the `app` name explicitly on every call (`aomi_select_app` returns context, it does not select anything server-side).

### Multi-step flows with `aomi_run`

When steps feed each other — a quote into a swap, a balance list into a loop — `aomi_run` executes the whole flow in one request. The program language is a small bash-like subset: capture (`q=$(tool k=v)`), pipes (`tool_a | tool_b k=$_.field`), `for` loops, field refs (`$q.quote_id`), and `return`. Only Aomi tool names are callable — no shell commands, conditionals, or arithmetic.

```text
q=$(khalani_quote from=USDC to=ETH amount=1000)
khalani_swap quote_id=$q.quote_id min_out=$q.amount_out
```

It returns `{ value, steps, error?, followups? }` — `steps` is a per-step trace for debugging; on error, fix the program and resubmit, or fall back to single `aomi_call_tool` calls.

### Follow-up routes

Tool results may include `followup.route_steps` — continuation calls a tool queued for the client (an approval before a swap, a commit after staging). Call them in order with `aomi_call_tool`, preserving opaque ids and calldata exactly. Every Aomi port describes route continuation the same way.

## How execution works

Each tool call runs inside a thread on the Aomi backend — the same kernel path chat uses, so the same skill gates and signing policy apply. Your MCP thread id is deterministic (derived from your account id), so all your MCP clients share one thread and its staged-transaction state. Pass an explicit `thread_id` to `aomi_call_tool` or `aomi_run` to target a different thread.

Transactions follow Aomi's stage-and-commit model: staging tools accumulate pending transactions; a commit declares the batch for wallet approval. **In production the commit always returns pending-approval — the server never signs autonomously.** Signing completes on a wallet-connected surface such as [chat.aomi.dev](https://chat.aomi.dev).

## Limits

- **Stateless transport.** One JSON-RPC message per POST; no SSE, no server sessions, no batching. Long-running server push is not available — `aomi_run` exists precisely so multi-step flows fit in one request.
- **Non-custodial, always.** MCP tool calls can read state, quote, simulate, and stage transactions. They cannot sign or move funds; wallet approval is a separate, user-visible step.
- **No network selector.** There is no browser wallet to pick a chain. When the user names a network, pass `chain_id` explicitly on staging tools (e.g. Sepolia is `11155111`).
- **One turn at a time.** If the thread is processing a chat turn, execution returns `409` — retry after the turn completes.
- **Request budget.** Calls are capped at 300 seconds.
- **Wallet required for execution.** No linked wallet means discovery-only; staged transactions fail until a wallet is linked at [chat.aomi.dev](https://chat.aomi.dev).
