title: "MCP"
description: "Connect an MCP client to Aomi, run account-owned agent sessions, and approve wallet requests without giving the server your keys."
---

Aomi exposes a hosted [Model Context Protocol](https://modelcontextprotocol.io)
server. Connect Codex, Claude Code, Cursor, or another MCP client to chat with
the Aomi agent, supervise long-running work, and continue conversations owned
by your Aomi account. You do not need to run a local MCP process.

The default endpoint follows the same conversational execution path as
[Aomi Chat](https://chat.aomi.dev). A separate direct endpoint exposes the
lower-level App and tool catalog when you need to orchestrate individual tools
yourself.

## Endpoints

| Environment | Agent chat | Direct tools | Transport |
| --- | --- | --- | --- |
| Production | `https://chat.aomi.dev/api/mcp` | `https://chat.aomi.dev/api/mcp/direct` | Streamable HTTP |
| Staging | `https://chat-staging.aomi.dev/api/mcp` | `https://chat-staging.aomi.dev/api/mcp/direct` | Streamable HTTP |

Use the agent-chat URL unless you specifically need the direct tool funnel.
Both endpoints require OAuth and execute as the authenticated Aomi account.

The server uses stateless Streamable HTTP: one JSON-RPC message per POST, JSON
responses, no SSE push, no MCP batch requests, and no server-issued MCP
session. Aomi conversation IDs and progress cursors are application data, so
you can resume work even though the transport is stateless.

<Note>
  Production and staging have separate account graphs. A sign-in, wallet link,
  or conversation in one environment does not carry over to the other.
</Note>

## Connect

<Tabs>
  <Tab title="Codex">
    Add the production server, then complete OAuth in your browser:

    ```bash
    codex mcp add aomi --url https://chat.aomi.dev/api/mcp
    codex mcp login aomi
    ```

    Codex desktop, the CLI, and the IDE extension share the same MCP
    configuration. You can also open `/mcp` to inspect the connection.
  </Tab>
  <Tab title="Claude Code">
    Add the production server:

    ```bash
    claude mcp add --transport http aomi https://chat.aomi.dev/api/mcp
    ```

    Run `/mcp`, select **aomi**, and choose **Authenticate** if the browser flow
    does not begin automatically.
  </Tab>
  <Tab title="Cursor">
    Add the server in `.cursor/mcp.json` for one project or
    `~/.cursor/mcp.json` globally:

    ```json
    {
      "mcpServers": {
        "aomi": {
          "url": "https://chat.aomi.dev/api/mcp"
        }
      }
    }
    ```
  </Tab>
  <Tab title="Another client">
    Configure a Streamable HTTP MCP server at
    `https://chat.aomi.dev/api/mcp`. The server publishes OAuth discovery on
    the same origin and supports dynamic client registration and PKCE.
  </Tab>
</Tabs>

After authorization, ask the client something such as:

```text
Ask Aomi for my USDC balance on Base, then explain the result.
```

Your client should call `aomi_chat`, retain the returned cursor, and call
`aomi_check` until the turn is complete or needs you.

## Agent-chat tools

The default `/api/mcp` endpoint exposes four tools:

| Tool | What it does |
| --- | --- |
| `aomi_chat` | Start a turn in a new or existing Aomi conversation. You can also specify an App and an authoritative chain context. |
| `aomi_check` | Return new messages and activity since the previous cursor. Continue until the status is `complete` or `awaiting_user`. |
| `aomi_interrupt` | Stop the turn currently processing in a conversation. |
| `aomi_list_sessions` | List recent conversations owned by the authenticated account so one can be resumed. |

### Run and supervise a turn

<Steps>
  <Step title="Start the turn">
    Call `aomi_chat` with the user's request. Omit `session_id` to create a new
    conversation, or pass an ID returned by `aomi_list_sessions` to continue
    one.

    ```json
    {
      "message": "Show my USDC balance on Base",
      "chain_context": { "family": "evm", "chain_id": 8453 }
    }
    ```
  </Step>
  <Step title="Keep the cursor">
    The response includes a self-contained cursor with the conversation ID and
    progress offsets. Pass that cursor to `aomi_check` without editing it.
  </Step>
  <Step title="Poll for progress">
    Each check returns only new transcript messages and activity. Continue
    while the status is `processing`. A longer App task may report tool and
    subtask progress across several checks.
  </Step>
  <Step title="Handle a wallet request">
    A status of `awaiting_user` includes a safe summary of each pending request
    and a handoff link. Let the user review and sign, then call `aomi_check`
    again. Do not report success until a later check returns the confirmed
    result.
  </Step>
</Steps>

Pass `chain_context` only when the active network is known. Aomi deliberately
does not invent a mainnet default for a headless client.

```json
{
  "family": "solana",
  "cluster": "solana:mainnet"
}
```

The accepted Solana values are `solana:mainnet`, `solana:devnet`, and
`solana:testnet`. For EVM, pass the positive integer chain ID listed on the
[EVM chains page](/concepts/chains/evm).

## Authentication and account ownership

The first unauthenticated request receives an OAuth challenge. Your MCP client
registers itself, creates a PKCE authorization request, and opens Aomi in your
browser. The connection then has two user-visible steps:

1. Sign in to Aomi with Para or Privy.
2. Review the client and OAuth scopes, then choose **Authorize** or **Deny**.

The resulting access token identifies your canonical Aomi account. Aomi
checks that identity again for every tool call. New conversations are created
under that account, and an existing conversation can be read, resumed, or
interrupted only by its owner.

Sign-in identity and signing authority are separate. Para or Privy proves
which Aomi account is connecting; it does not give an MCP client blanket
permission to sign. The account remains the owner of conversations, Apps,
usage, and linked wallets. Each wallet keeps its own address, chain family,
provider, and signing policy. Read [Accounts and wallets](/concepts/accounts-and-wallets)
for the complete model.

<Warning>
  Authorize only MCP clients you trust. An authorized client can start agent
  work and inspect the Aomi conversations it creates or resumes as your
  account. Wallet policy still controls whether an onchain request can be
  signed.
</Warning>

## Wallet connection and signing

Discovery and offchain agent work can run without a wallet. For onchain work,
link an EVM or Solana wallet to the same Aomi account at
[chat.aomi.dev](https://chat.aomi.dev). Connecting a wallet to one browser tab
is not enough: linking proves that the public address belongs to the account
and makes it available to other authenticated surfaces, including MCP.

At the start of an MCP turn, Aomi loads the account's linked EVM and Solana
addresses. An explicit `chain_context` supplies the network; the wallet record
does not silently choose one. If the account has no compatible linked wallet,
the agent can explain or discover tools, but it cannot complete the onchain
request.

MCP remains non-custodial:

- The MCP response contains only review fields such as request ID, kind,
  destination, value, chain or cluster, and description.
- Private keys, seed phrases, raw signing material, and reusable signatures do
  not pass through MCP.
- A pending request follows that wallet's current signing policy. MCP does not
  switch wallets or make a locked or manual wallet more permissive.

When `aomi_check` returns `awaiting_user`, approve the request in either place:

<Tabs>
  <Tab title="Aomi portal">
    Open the returned `portal_url`, inspect the request in its conversation,
    and approve or reject it with the linked wallet. Return to the MCP client
    afterward so it can call `aomi_check` again.
  </Tab>
  <Tab title="Aomi CLI">
    Authenticate the CLI to the same account, resume the MCP conversation, and
    sign the pending request:

    ```bash
    npx @aomi-labs/client@latest account login --provider para
    npx @aomi-labs/client@latest session resume <session-id>
    npx @aomi-labs/client@latest tx list
    npx @aomi-labs/client@latest tx sign <request-id>
    ```

    Use your installed `aomi` command instead of
    `npx @aomi-labs/client@latest` if the CLI is already installed.
  </Tab>
</Tabs>

Signing is a handoff, not the end of the MCP turn. After approval, the client
must call `aomi_check` again to observe submission, confirmation, rejection, or
failure. See [Signing](/security/signing) for the wallet-side lifecycle.

## Advanced: direct App tools

Connect to `/api/mcp/direct` when you want the low-level catalog and execution
funnel instead of an Aomi agent conversation. This endpoint exposes ten tools:

| Stage | Tools |
| --- | --- |
| Understand the account and catalog | `aomi_get_agent_context`, `aomi_list_apps`, `aomi_search_apps` |
| Narrow to a capability | `aomi_select_app`, `aomi_list_namespaces`, `aomi_list_tools`, `aomi_search_tools` |
| Inspect and execute | `aomi_describe_tool`, `aomi_call_tool`, `aomi_run` |

The direct endpoint is also stateless. Pass the App explicitly on each call;
`aomi_select_app` returns context but does not change server state. Use
`aomi_call_tool` for one action and `aomi_run` when intermediate results feed
later tool calls. Transactions still follow the same account ownership,
wallet policy, and user-visible signing boundary described above.

## Limits

- **One active turn per conversation.** Interrupt or wait for the current turn
  before starting another one in the same session.
- **Explicit network context.** Pass a known EVM chain ID or Solana cluster.
  Omit the field instead of guessing.
- **User-visible signing.** A wallet request may pause the turn until the user
  acts in the portal or an authenticated CLI.
- **Request budget.** Each MCP request is capped at 300 seconds. Use
  `aomi_check` to supervise work that continues beyond one request.
- **Stateless transport.** Persist the returned Aomi conversation ID and cursor
  rather than relying on an MCP transport session.
