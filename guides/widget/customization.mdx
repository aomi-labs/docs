The widget uses the same reviewed interface as the Portal. Change its dimensions
and optional controls through props:

```tsx
"use client";
import { AomiWidget } from "@aomi-labs/widget";
import "@aomi-labs/widget/styles.css";
export default function Assistant() {
  return <AomiWidget applicationId="123" height="100dvh" theme="dark" showSidebar={false} features={{ library: false }} />;
}
```

`theme` is `"light"`, `"dark"` or `"system"` (the default, which follows the
visitor's operating system) and applies per instance. Compiled styles,
dialogs, popovers, tooltips and notifications stay inside that widget's scope.
Two instances can use different themes on the same page. Embeds omit the product
switcher by default; composed first-party hosts can pass `products` to the frame.

## Routing

`applicationId` identifies the hosted App. `routing` chooses Auto or a Direct
target independently:

```tsx
"use client";
import { AomiWidget } from "@aomi-labs/widget";
import "@aomi-labs/widget/styles.css";
export default function Assistant() {
  return <AomiWidget applicationId="123" routing={{ defaultMode: "direct", targets: [{ mode: "direct", apps: [{ applicationId: 456 }] }] }} />;
}
```

## Thread selection

Pass `initialThreadId` to open a specific existing chat on mount. For a controlled
integration, store `threadId` in your host and update it through `onThreadChange`:

```tsx
"use client";
import { useState } from "react";
import { AomiWidget } from "@aomi-labs/widget";
import "@aomi-labs/widget/styles.css";
export default function Assistant() {
  const [threadId, setThreadId] = useState<string | undefined>();
  return <AomiWidget applicationId="123" threadId={threadId} onThreadChange={setThreadId} />;
}
```

The callback reports user thread selection without echoing controlled prop
changes. Switching chats preserves the shell, each chat's draft and its display
state within the same account. By default, selection persists for a signed-in
account or when you supply a persistence key or scope. Anonymous embeds
otherwise keep it in memory. Set `persistThread={false}` to keep selection in
memory explicitly. Use `threadPersistenceScope` to add
your host's tenant or user scope, or `threadPersistenceKey` for an explicit
storage key. Persisted selection does not authorize access to another account's
chat.

## Composed hosts

```tsx
"use client";
import { AomiFrame } from "@aomi-labs/widget/frame";
import "@aomi-labs/widget/styles.css";
export default function Assistant() {
  return <AomiFrame.Root backendUrl="https://chat.aomi.dev" applicationId="123"><AomiFrame.Composer /></AomiFrame.Root>;
}
```

Use the compiled `AomiFrame` entry and its compound components when your host
provides its own chrome. Pass `backendUrl` explicitly, or use `""` for a
same-origin API. Account management transport and wallet-provider configuration
remain explicit host inputs. Prefer the standalone widget for ordinary embeds.

Add `aui-suggestions-marquee` to the composed frame's `className` to enable the
two moving recommendation rows with faded edges. The rows use the original
30-second and 72-second animations. They wrap without animation when the visitor
requests reduced motion.

Browser preferences are scoped by backend, App and account where available.
Old preference keys migrate once to the first scope that reads them. API keys
stay in memory by default. First-party frame hosts can explicitly opt into scoped
session storage; plaintext local-storage API keys are removed and never written
back.

## Build a headless UI

Choose the headless library when props, themes, and composition are not enough. Aomi continues to provide thread, chat, user, event, notification, and wallet-request state. You provide every visible interaction.

### Install the library

```bash
npm install @aomi-labs/react @assistant-ui/react@0.14.26
```

### Add the runtime provider

```tsx
import { AomiRuntimeProvider, type RuntimeAccount } from "@aomi-labs/react";

export function Providers({ children, account }: {
  children: React.ReactNode;
  account?: RuntimeAccount | null;
}) {
  return (
    <AomiRuntimeProvider
      backendUrl="https://chat.aomi.dev"
      applicationId="123"
      account={account}
    >
      {children}
    </AomiRuntimeProvider>
  );
}
```

Pass the confirmed account as `{ kind: "user", id }` or `{ kind: "guest", id }`.
Use `undefined` while resolving the session and `null` when no account is signed
in. This scopes displayed account data; it does not supply authentication.
Configure credentials through `clientOptions` for your chosen transport.

### Your responsibilities

A headless interface must provide:

- Thread navigation and message rendering.
- Composer, streaming, cancellation, and error states.
- Wallet connection and network selection.
- Transaction-call and fee disclosure.
- Explicit approval and rejection controls.
- Owner and network validation before signing.
- Submitted, confirmed, expired, and failed operation states.

<Warning>
  Returning a generic transaction result is not enough. Your interface must narrow each action by `action.request.type`, show the exact request, and return the result that type expects. Prefer `AomiWidget` unless you need to own the full approval experience.
</Warning>

## Hooks

All hooks must run beneath `AomiRuntimeProvider`.

### Chat and threads

| Hook | Purpose |
| --- | --- |
| `useAomiRuntime` | Unified chat, thread, user, notification, event, and wallet API |
| `useThreadContext` | Low-level thread state and operations |
| `useCurrentThreadMetadata` | Metadata for the active thread |

Read active-thread messages with `useAomiRuntime().getMessages()`.

### User and wallet controls

| Hook | Purpose |
| --- | --- |
| `useUser` | Canonical user and wallet state |
| `useControl` | Combined App, model, API-key, and secret controls |
| `useApiKey` | API-key state and actions |
| `useAuthEndpoints` | Available Apps and models |
| `usePerThreadControl` | Per-thread App and model selection |

### Events and notifications

| Hook | Purpose |
| --- | --- |
| `useNotification` | Notice, success, wallet, and error messages |

Read ordered backend events from `useAomiRuntime().events` and the active lifecycle from `turnState`. `pendingActions` contains canonical Actions; narrow on `action.request.type` before reading its payload. Use the exported TypeScript types as the source of truth for complete signatures and payloads.

## Complete custom UI example

This starter owns message rendering, the composer, cancellation, and the visible wallet-request count:

```tsx
"use client";

import { useState, type FormEvent } from "react";
import { useAomiRuntime } from "@aomi-labs/react";

export function CustomChat() {
  const [input, setInput] = useState("");
  const {
    currentThreadId,
    getMessages,
    sendMessage,
    isRunning,
    cancelGeneration,
    pendingActions,
  } = useAomiRuntime();

  const messages = getMessages(currentThreadId);

  async function submit(event: FormEvent) {
    event.preventDefault();
    const text = input.trim();
    if (!text || isRunning) return;
    setInput("");
    await sendMessage(text);
  }

  return (
    <main>
      <section aria-live="polite">
        {messages.map((message, index) => (
          <article key={index} data-role={message.role}>
            <strong>{message.role}</strong>
          </article>
        ))}
      </section>

      <form onSubmit={submit}>
        <input
          value={input}
          onChange={(event) => setInput(event.target.value)}
          disabled={isRunning}
        />
        {isRunning ? (
          <button type="button" onClick={cancelGeneration}>Stop</button>
        ) : (
          <button type="submit">Send</button>
        )}
      </form>

      <p>{pendingActions.length} actions need review</p>
    </main>
  );
}
```

Add an approval component for every action kind your App can produce. Show the calls, signatures, owner, network, simulation evidence, and terminal status available on the request.
