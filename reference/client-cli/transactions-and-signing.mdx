The backend builds wallet requests. The client CLI stores them locally until you simulate or sign them. Start with the [Client CLI overview](/reference/client-cli), or use the [command reference](/reference/client-cli/commands) for every flag and environment variable.

## Transaction flow

The backend builds transactions. The CLI persists them locally, then signs and submits them when you choose.

<Steps>
  <Step title="Chat and queue a request">
    ```bash
    aomi chat "swap 1 ETH for USDC on Uniswap" --public-key 0xYourAddr --chain 1
    ```

    When the agent needs a signature, the request is queued locally as `tx-1`. The CLI prints the destination, value, and chain.
  </Step>

  <Step title="Inspect pending transactions">
    ```bash
    aomi tx list
    ```

    ```text
    Pending (1):
      ⏳ tx-1  to: 0x3fC91A3afd70395Cd496C647d5a6CC9D4B2b7FAD  value: 1000000000000000000  chain: 1  (2:14:07 PM)
    ```
  </Step>

  <Step title="Simulate before you sign">
    ```bash
    aomi tx simulate tx-1
    ```

    The backend simulates the batch atomically against a fork snapshot when available. Otherwise, it uses independent `eth_call` requests. The command prints each step's result, gas, revert reason, and service fee quote. No funds move.
  </Step>

  <Step title="Sign and submit">
    ```bash
    aomi tx sign tx-1 --private-key 0xYourPrivateKey
    ```

    The CLI signs locally, submits, prints the hash, and notifies the backend so the conversation continues with the result.
  </Step>
</Steps>

The same flow handles EIP-712 typed-data signatures. When the backend asks for a typed signature (for example a CoW Protocol order or a permit approval), it appears in `aomi tx list` with kind `eip712_sign`, and the same `aomi tx sign` command produces the signature. EIP-712 requests sign one at a time; batching is for transaction requests only.

### Solana requests

Solana wallet requests flow through the same queue. `aomi tx list` shows them alongside EVM requests; `aomi tx sign` handles kinds `solana_sign`, `solana_sign_message`, and `solana_send`. Sign-and-send requests are submitted and confirmed through the cluster's default RPC (`--rpc-url` overrides it); sign-only requests return the signed bytes to the backend.

```bash
aomi wallet set --solana 5Kd3N...           # persist the keypair once
aomi tx sign svm:tx-1                       # or pass --solana-private-key per command
```

The keypair is accepted as a base58 64-byte secret key (Phantom or Solflare export) or a JSON byte array (`solana-keygen` output), via `--solana-private-key` or `SOLANA_PRIVATE_KEY`. Select the cluster with `--cluster mainnet-beta|devnet|testnet` or `AOMI_SOLANA_CLUSTER`; `aomi wallet set --solana` persists it (default `solana:mainnet`), so you only need the flag to override the saved choice. One `aomi tx sign` invocation handles either Solana or EVM requests, not a mix; multiple Solana requests execute sequentially, and a confirmed transaction is not rolled back if a later one fails.

## Signing

Local signing is direct EOA execution: the CLI signs with your key and submits through an RPC. That is the default and only local mode.

| Flag                         | Behavior                                                                                             |
| ---------------------------- | ---------------------------------------------------------------------------------------------------- |
| (default) / `--eoa`          | Local EOA signing and submission                                                                     |
| `--aa`                       | Rejected. AA execution now runs in the backend lane; the command errors and tells you to use `--eoa` |
| `--aa-provider`, `--aa-mode` | Rejected on `tx sign` for the same reason                                                            |

Account-abstraction execution (EIP-4337 and EIP-7702) moved out of the CLI into the backend AA lane. The `AOMI_AA_PROVIDER` (`alchemy` or `pimlico`) and `AOMI_AA_MODE` (`4337` or `7702`) environment variables record your AA preference; `aomi chat` syncs that preference to backend user state so the backend can route smart-account execution accordingly. They do not change how `aomi tx sign` executes.

```bash
aomi tx sign tx-1 --private-key 0xYourPrivateKey --rpc-url https://eth.llamarpc.com
aomi tx sign tx-1 tx-2                      # batch of transaction requests
aomi tx sign evm:tx-1                       # chain-qualified when IDs collide
```

Details that hold during `tx sign`:

- Before executing, the CLI simulates the batch to validate it and fetch the service fee quote. A quoted fee is appended as a separate transfer after your calls; its hash is reported separately as `Fee tx:` so the action's hash stays clean.
- If simulation is unavailable, signing proceeds without fee injection.
- If the signer address differs from the session's `--public-key`, the CLI warns and updates the session to the signing key.
- A single `--rpc-url` override is rejected for a multi-sign batch that spans multiple chains.

## Relevant configuration

Use `--public-key` to give the agent your EVM wallet address; it must be a 0x-prefixed address, and a Solana address here is rejected. Use `--private-key` or `PRIVATE_KEY` only when you are ready to sign locally. For Solana, use `aomi wallet set --solana`, `--solana-private-key`, or `SOLANA_PRIVATE_KEY`. Use `--rpc-url` to override transaction submission for the selected chain.

<Warning>
  Never paste private keys into chat prompts. Pass them only through CLI flags, environment variables, or the protected local state created by `aomi wallet set`.
</Warning>

See [Commands and configuration](/reference/client-cli/commands#flags-and-environment-variables) for the complete flag table and local state behavior.
