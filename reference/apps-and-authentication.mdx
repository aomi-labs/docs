title: "Apps and authentication"
description: "Understand App selection, caller identity, App access, user credentials, sessions, and wallet authority."
---

An Aomi **App** is the deployed, user-selectable unit. Builders author a Rust plugin; after deployment, users and clients select the resulting App through Agent or Pipeline.

Keep these boundaries separate:

| Boundary         | What it controls                                                                  |
| ---------------- | --------------------------------------------------------------------------------- |
| Caller identity  | Which guest or account owns sessions and calls.                                   |
| App selection    | Which deployed App handles Direct work, or whether Auto routing chooses one.      |
| App access       | Whether the caller can use a selected App. A provisioned App key can be required. |
| App credentials  | User-owned secret slots declared by one App, such as an exchange API key.         |
| Wallet authority | Which exact Action a wallet can sign or submit.                                   |

Authentication does not grant wallet signing authority. A wallet address does not prove account ownership. A session ID continues work but is not an authentication credential.

## Select an App

Agent calls use Auto routing by default. Select Direct routing only when the caller intentionally pins one App:

```bash
aomi chat "compare routes" --new-session
aomi chat "quote this swap" --mode direct --app zerox --new-session
aomi chat "use this hosted App" --application-id 2936682 --new-session
```

An Application ID is the canonical identity for a hosted App. An App name can be ambiguous across hosted deployments, so use the ID returned by your environment's catalog when identity matters.

Pipeline calls are already explicit. Discover the App and operation before invoking it:

```bash
aomi pipeline apps
aomi pipeline operations --app aave
aomi pipeline operation supply --app aave
```

## Authenticate the caller

Choose identity based on the host:

| Host                | Normal credential                      |
| ------------------- | -------------------------------------- |
| Node.js evaluation  | Automatic guest session.               |
| CLI, bot, or server | OAuth device grant.                    |
| Same-origin browser | First-party account session.           |
| Cross-origin widget | Origin-bound widget session.           |
| MCP client          | OAuth with PKCE for the exact MCP URL. |

OAuth grants bind to exact resources. Tokens for `/v1/agent`, `/v1/pipeline`, `/v1/account`, `/v1/agent/mcp`, and `/v1/pipeline/mcp` are not interchangeable.

The CLI manages device grants with:

```bash
aomi account login
aomi account whoami
aomi account logout
```

See [Authentication](/integrate/authentication) for guest, OAuth, browser, and widget setup. See the [authentication reference](/api-reference/authentication) for resource and scope failures.

## App access keys

Some provisioned Apps require an App access key in addition to caller authentication. In the TypeScript client, `apiKey` sends the `Aomi-App-Key` header. In the CLI, use `--api-key` or `AOMI_API_KEY`.

```bash
aomi chat "run the selected App" \
  --mode direct \
  --app my-app \
  --api-key "$AOMI_API_KEY"
```

An App key selects an App access boundary. It does not replace an OAuth account grant, own an Agent session, or authorize a wallet signature.

<Warning>
  Do not copy older examples that use `X-API-Key`, `/api/chat`, or a message in
  the query string. Current Agent calls use the versioned `/v1/agent` resource
  and the `Aomi-App-Key` header when an App key is required.
</Warning>

## Persistent App credentials

An App can declare user-owned credential slots. For example, a CEX App can declare `EXCHANGE_API_KEY` without exposing the saved value to the Agent or to later read calls.

Merged client `0.9.4` source adds these CLI commands:

```bash
aomi app list
aomi app credentials status <application-id>
aomi app credentials set <application-id> EXCHANGE_API_KEY
aomi app add <application-id>
```

`set` and `replace` read one value from a hidden terminal prompt. In a non-interactive process they read stdin. The value is never a positional argument, and status responses contain slot names and configuration state rather than saved values.

<Note>
  npm `latest` is `0.7.6` as of September 22, 2026. The App installation and
  persistent credential commands require a `0.9.4` or newer release plus
  matching `/v1/account` support in the target environment.
</Note>

The Account resource uses separate App and credential scopes. Agent or Pipeline authorization alone does not authorize credential changes. Guests cannot manage persistent App credentials.

## Temporary session secrets and model BYOK

Temporary session secrets use another store:

```bash
aomi secret add TENDERLY_ACCESS_TOKEN=value
aomi secret list
aomi secret clear
```

`secret add` transmits each value to Aomi and stores an opaque handle in the local session. Those values are scoped to the Agent session rather than one installed App.

Model-provider BYOK is separate again. The REPL `/key` command and root `--provider-key` support `anthropic`, `openai`, and `openrouter`. `--inference-funding user_byok` asks the account to use its saved model-provider key for inference.

## Sessions and wallets

An Agent session is a conversation owned by the authenticated caller. Reuse its session ID to continue work. Do not use a wallet address or App key as a session-ownership key.

Wallet context tells an App which account and chain to build for:

```bash
aomi chat "show my Base balances" \
  --public-key 0xYourAddress \
  --chain 8453
```

The public address is context. Signing remains a separate Action review. See [Transactions and signing](/reference/client-cli/transactions-and-signing) for the wallet boundary.
