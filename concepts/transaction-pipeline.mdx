Every onchain action follows one ordered pipeline:

**build → simulate → sign → broadcast**

This pipeline is an abstraction over both EVM and SVM execution. The two
environments encode transactions differently, but they share the same control
model. Each action begins from observable chain state. It proposes a state
transition and produces side effects only after verification and authorization.

The model can choose tools and prepare the proposed transition. It cannot sign
or submit the action on its own. A failed simulation stops the flow before your
wallet receives a request. This contract applies to interactive chat and MCP.
It also covers [asynchronous tasks](/concepts/asynchronous-tasks) and CLI
commands. Every surface therefore follows the same safety boundary and produces
the same audit trail.

## Pipeline at a glance

| Stage | What happens | Result |
|---|---|---|
| Build | A tool creates the exact transaction. | A staged record with a stable id. |
| Simulate | Aomi runs the staged transaction against current chain state. | Results, warnings, and a fee quote. |
| Sign | Aomi checks the wallet policy and requests approval. | A signature or a clear denial. |
| Broadcast | The signed payload is submitted and tracked. | A transaction hash and confirmation status. |

Each stage uses the same staged record. Later stages cannot change the target or
value. They also cannot change the calldata or batch order. What you sign is
what Aomi simulated.

## Build Stage

The build stage creates the exact transaction. It chooses the contract and
function. It also sets the arguments, value, and chain.

Aomi can build calldata in two ways:

1. A typed encoder accepts a function signature such as
   `approve(address,uint256)`. It rejects an invalid address or amount before
   the transaction reaches simulation.
2. A routing service can return complete calldata. Aomi preserves those bytes
   instead of rebuilding them.

Here is a staging call for “Approve 500 USDC for the Uniswap router.” The model
provides readable values. The runtime produces the encoded bytes.

```jsonc
{
  "to": "0xA0b86991c6218b36c1d19D4a2e9Eb0cE3606eB48",      // USDC contract
  "description": "Approve 500 USDC for Uniswap V3 Router",  // label shown to the user
  "data": {
    "encode": {
      "signature": "approve(address,uint256)",
      "args": [
        "0xE592427A0AEce92De3Edee1F18E0157C05861564",       // router
        "500000000"                                         // 500 USDC in base units
      ]
    }
  },
  "value": "0",
  "kind": "erc20_approve"
}
```

Aomi adds the wallet address and chain id from the active context. It stores the
finished transaction as a staged record. The model cannot replace the encoded
bytes during a later step.

A multi-step action becomes one ordered batch. For example, a swap can contain
an approval followed by the swap itself. Simulation and signing preserve that
order.

## Simulation Stage

Simulation checks the staged batch before a key can sign it.

For EVM chains, Aomi runs the batch against a private copy of current chain
state. Each step sees the state created by the previous step. An approval can
therefore affect the swap that follows it. The live chain remains unchanged.

The result includes:

- success or failure for each step
- gas usage
- decoded revert reasons when available
- safety findings from protocol guards
- the Aomi fee as a separate batch item

A critical safety finding blocks the transaction. A lower-risk finding appears
as a warning. The wallet receives the same batch that passed simulation.

Solana uses LiteSVM with current program and account data. It can fall back to
RPC simulation when LiteSVM cannot load a program. Solana verifies each staged
transaction on its own. It does not yet provide the stateful multi-transaction
rehearsal used for EVM batches. See [Solana bundle](/concepts/solana-bundle)
for instruction assembly, explicit simulation, and submission routing.

## Sign Stage

A successful simulation still moves no funds. Aomi checks the wallet's current
signing policy when the commit begins.

| Mode | Result |
|---|---|
| `manual` | Your wallet asks for approval. |
| `auto` | An embedded wallet signs under a delegated grant. |
| `client-auto` | Your key-holding client signs at the edge. |
| `denied` | Aomi blocks the request. |

A wallet with no policy fails closed. A read-only thread cannot sign. See
[Permission model](/security/permission-model) for the full rules.

Smart-account wallets use the same gate. EIP-7702 executes the batch from your
delegated address. ERC-4337 executes it from your smart account. The full batch
becomes one prepared operation after any required first-use account
authorization. A partial batch cannot execute. See
[Account abstraction](/concepts/account-abstraction) for the owner, signer,
executor, and sponsorship flow.

Signature-only requests use the same queue. EIP-712 permits and offchain orders
use `evm_commit_message`. Solana can request a transaction signature, a message
signature, or sign-and-send.

## Broadcast and confirm

The submission path depends on the signer:

- With manual signing, your wallet signs and submits. It returns the transaction
  hash to the thread.
- With delegated signing, the runtime submits the operation and waits for its
  receipt.
- On Solana, the wallet can sign and submit in one step. It can also return a
  signature for the client to submit.

A pending transaction stays visible until it confirms or fails. The final
result includes the transaction hash or the reported error. Aomi reports its
fee separately from the trade.

## Tool namespaces

An App opts into transaction tools through namespaces. A namespace is a named
and versioned tool set. It also tells Aomi which wallet family the App needs.

```rust
dyn_aomi_app!(
    app = MyApp,
    name = "my-app",
    version = "0.1.0",
    preamble = PREAMBLE,
    tools = [
        tool::QuoteTool,
        tool::SwapTool,
    ],
    namespaces = ["evm-core", "aomi-core"]
);
```

### aomi-core

`aomi-core` provides chain-independent host tools. The default App includes it.
A custom App can opt in.

| Tool | What it does |
|---|---|
| `ask_authorization` | Ask the user to grant or change wallet authorization. |
| `get_authorization` | Read the current authorization state. |
| `revoke_approval` | Revoke a delegated signing approval. |
| `brave_search` | Search the web. |
| `list_skills` | List skills that can be activated. |
| `schedule_cron` | Save an intent to run later or on a schedule. |
| `spawn_thread` | Run an intent in a background thread now. |
| `wake_on_condition` | Run an intent when a chain condition becomes true. |
| `thread_return` | Report a background thread's final status. |

The scheduling tools support
[asynchronous tasks](/concepts/asynchronous-tasks).

### evm-core

`evm-core` provides the standard EVM transaction flow.

| Stage | Tool | What it does |
|---|---|---|
| Read | `get_time_and_onchain_context` | Read the active time, chain, and wallet. |
| Read | `get_account_info` | Read balances and account state. |
| Read | `get_contract` | Read a contract ABI and resolve proxies. |
| Read | `encode_and_call` | Encode and execute a read-only contract call. |
| Read | `sync_chain` | Update the simulation state to the live chain tip. |
| Build | `evm_stage_tx` | Create a staged transaction record. |
| Simulate | `simulate_batch` | Run the staged batch and report each result. |
| Sign | `evm_commit_txs` | Request a signature for staged transaction ids. |
| Sign | `evm_commit_message` | Request an EIP-712 signature. |

### SVM namespaces

Solana separates read tools from two write formats.

| Namespace | Purpose | Tools |
|---|---|---|
| `svm-reads` | Read accounts, token holdings, programs, and context. | `svm_get_context`, `svm_get_account_info`, `svm_get_token_holdings`, `svm_get_program` |
| `svm-write-ix` | Build from instruction lists. | `svm_stage_ix`, `svm_simulate_ix`, `svm_commit_ix`, `svm_sign_data` |
| `svm-write-tx` | Accept a complete transaction from a venue. | `svm_stage_tx`, `svm_simulate_tx`, `svm_commit_tx`, `svm_sign_data` |
| `svm-core` | Include all SVM tools. | The union of the three namespaces above. |

`svm-write-ix` fits services that return instructions. Jupiter's
`/swap-instructions`, Orca, and Marinade use this pattern. `svm-write-tx` fits
services that return a complete transaction. Jupiter's `/swap` and Raydium use
this pattern.

The namespace selects the available tools. It does not decide who signs. The
wallet's [Permission model](/security/permission-model) decides that at commit
time.

## A useful comparison

A coding agent and an Aomi agent follow a similar control loop. Both read state
and propose a change. Both verify the result before committing. The authority
model differs.
A coding agent can write to its environment. An Aomi agent must ask a wallet to
sign.

| Step | Coding agent | Aomi agent |
|---|---|---|
| State | Codebase and operating system. | Chain state and wallet state. |
| Read | Inspect files and processes. | Call read-only chain tools. |
| Propose | Prepare a file edit. | Create a staged transaction. |
| Verify | Run tests. | Simulate against chain state. |
| Commit | Write to the environment. | Ask the wallet to sign. |
| Judge | Check the test result. | Check balances, events, and receipts. |

This comparison is adapted from
[AomiBench v0.1](https://aomi.dev/research/aomibench-v0-1).

## The guarantee

The runtime enforces the stage order. A commit accepts staged record ids. It
does not accept replacement calldata. It also rejects a reordered batch because
that order did not pass simulation.

**A transaction that fails simulation never reaches a signature.**
