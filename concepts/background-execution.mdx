---

An Aomi agent does not stop existing when you close the tab. A thread can
persist an intent — run this later, run this every day, run this when a
condition becomes true — and the runtime executes it server-side. This is
the mechanism behind the demo caption "persisted as a recurring intent",
and behind background strategies, scheduled rebalances, DCA, and stop-loss
style triggers.

## Three ways to defer work

Ask the agent in plain language; it maps the request onto three tools:

| Tool | What it persists |
| --- | --- |
| `schedule_cron` | A one-shot or recurring intent: the instruction text, the target App, a snapshot of your thread's user state, the trigger time, and an optional recurrence. Timezone-aware — recurrence anchors to your configured timezone, DST handled, and the anchor comes from your settings, never from the model. |
| `spawn_thread` | Fire-and-forget "run this now, in the background": a one-shot intent due immediately, picked up on the next clock tick. |
| `wake_on_condition` | A guarded intent: a read-tool probe plus a comparison ("when the health factor drops below 1.1", "when ETH crosses X"), polled on a cadence, optionally recurring with re-arm hysteresis, optionally expiring. |

A schedule is a **durable database row, not a sleeping thread**. Each fire
spawns a fresh agent thread carrying the saved intent and context.

## Crash-safe by construction

The runtime clock ticks every 30 seconds, claims due intents under an
atomic lease, and runs each in a detached thread:

- A crash mid-run doesn't lose the intent — the lease lapses and a later
  tick re-claims it.
- Three failed attempts dead-letter the job: it is kept for inspection and
  never fired again silently.
- Recurrence anchors to the original trigger time, so a slow run does not
  drift your daily 9am rebalance.
- For risky condition fires, an optional **confirm judge** — a detached,
  read-only agent pass — must return an explicit yes before the intent
  executes. A no, a stall, or a crash fails closed without burning an
  attempt.

## Signing in an unattended run

Nothing about scheduling pre-grants signing. Authority is resolved from
your [per-wallet signing policy](/concepts/signing-policy) at execution
time, each time:

- A wallet armed to `auto` (embedded, delegated, revocable) signs without a
  prompt — this is what lets a strategy run while you sleep.
- A `manual` wallet stages the transaction for your approval, exactly like
  an interactive turn.
- A read-only thread cannot sign at all, and neither can anything it
  spawns.

Revoking a grant between fires takes effect immediately: the next fire
resolves the policy fresh and stops at the signature.

## Inspecting and cancelling

Your scheduled intents are account-scoped: list and cancel them through the
account API, or just ask the agent what it has scheduled. These tools ship
in the `aomi-core` namespace — the default App includes them; a custom App
opts in.
