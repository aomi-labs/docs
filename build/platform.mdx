[build.aomi.dev](https://build.aomi.dev) is the hosted control plane for Aomi Apps.
You sign in with GitHub, and every deploy-lifecycle operation the
[`aomi-build` CLI](/build/toolchain/aomi-build) performs — connect, deploy, activate,
status — has a web counterpart here, plus the operating surfaces that only make
sense in a dashboard: deployment history, environment secrets, model provider
keys, bot integrations, transactions, usage, logs, and metrics.

<Info>
  The platform and the CLI drive the same backend lifecycle. Nothing you do in
  one is invisible to the other: a project connected by `aomi-build connect`
  shows up in the Projects list, and an app activated from the browser answers
  `aomi-build deploy status`.
</Info>

## The words the platform uses

| Term            | Meaning                                                    |
| --------------- | ---------------------------------------------------------- |
| **Project**     | A GitHub repository connected to Build.                    |
| **App**         | A deployable unit inside a project. One repo can ship several. |
| **Deployment**  | A published build of an app that can go live.              |
| **Environment** | The API keys and secrets configured for an app. Not billing. |

## Ship your first app from the browser

The web path creates the repo for you. It forks Aomi's template into your own
GitHub account, so you own the code from the first commit.

<Steps>
  <Step title="Sign in with GitHub">
    Go to [build.aomi.dev](https://build.aomi.dev) and sign in. The whole
    console is scoped to this GitHub identity.
  </Step>
  <Step title="Install the Aomi Build GitHub App">
    **New app** walks you through installing the GitHub App on your **personal
    account**. One-click creation does not work on an organization install — if
    you installed on an org, the wizard stops and asks you to install on your
    personal account instead. (Org-owned repos can still deploy through the
    [CLI](/build/toolchain/aomi-build).)
  </Step>
  <Step title="Create">
    Build forks the template repository (`aomi-labs/playground-example`) into
    your account and connects it as a Project.
  </Step>
  <Step title="Deploy and activate">
    The wizard deploys the commit, waits for the platform build, and activates
    the release onto the live runtime. If the app declares required secrets in
    its manifest, the wizard blocks activation until you set them — so an app
    never goes live with an empty key it needs.
  </Step>
  <Step title="Live">
    The final step links straight into [chat.aomi.dev](https://chat.aomi.dev)
    with your app selected, so the first test message is one click away.
  </Step>
</Steps>

<Note>
  The web wizard only creates template forks. To connect a repo you already
  have — your own code, your own history — use
  [`aomi-build connect`](/build/toolchain/aomi-build). Once connected, the repo
  appears as a Project here and gets the full web lifecycle below.
</Note>

## The project page

Every Project has one page with five tabs:

* **Home** — live status, the environment at a glance, a usage meter, and (when
  the app prices its tools) a monetization card. The page computes the one next
  action that matters — *Redeploy from Linked Repository*, *Open Environment*,
  *Upgrade SDK* — and puts it on a single button.
* **Deployments** — the release history for this project. Each deployment can
  be **promoted** or **deactivated** from its row.
* **Providers** — which of your model keys fund this project's apps.
  Key management itself lives on the global [Providers](#model-provider-keys) page.
* **Environment** — one list merging the variables the app's manifest declares
  (with descriptions and required flags) and the keys already configured in the
  vault. Values are write-only: you can set, replace, or delete a secret, but
  the platform never echoes one back.
* **Chat** — your live app, embedded from chat.aomi.dev with the app
  preselected. If the app's SDK is outdated the tab blocks and points you to
  the upgrade instead.

### Redeploy

**Redeploy from Linked Repository** runs deploy → platform CI → activate
against the repo's current head, and the page tracks each phase until the
runtime confirms the release is loaded (it polls status for up to eight
minutes before reporting a timeout).

### When the platform bumps the SDK

The backend pins a required `aomi-sdk` version, and it moves. When your project
falls behind, Build shows the required version and offers a one-click upgrade:
it opens a pull request on **your** repository (branch `aomi/sdk-<version>`)
that rewrites the pin, waits for you to merge it, then redeploys. The endpoint
is idempotent — clicking again while the PR is open reuses it. If your
`Cargo.lock` has to be regenerated locally, the flow says so and hands you the
exact command instead of guessing. The CLI equivalent is `aomi-build sdk fix`.

## Model provider keys

**Account → Providers** holds your own LLM keys — OpenAI, Anthropic, and
OpenRouter — so your apps' model spend routes through accounts you control.
Key material is write-only: after you paste a key, only its stored prefix is
ever displayed. Each key can be assigned to specific projects, and each key
row shows the tokens and cost it has accrued.

## Integrations

**Account → Integrations** turns a deployed app into a bot. Telegram is live:
paste a BotFather token, attach one or more apps, pick the primary one and a
thread mode, and Aomi hosts the bot and wires the webhook — the full walkthrough
is [Put your App on Telegram](/build/telegram-bot). You can re-edit a
bot's attached apps at any time without re-entering the token. Discord and
Slack appear on the page but are not available yet.

## Operate

The Operate section is read-your-own-apps observability, scoped to the
projects you own:

* **Deployments** — deployment history across all your projects, filterable by
  project and by current/previous status.
* **Transactions** — the onchain transactions your apps' users execute, with
  hash, status, and fee detail per row (EVM and SVM).
* **Usage** — credits and tokens per app per day. When your apps price their
  tools, this page also carries the **partner payments ledger**: what each
  priced tool charges, who the beneficiary is, and the accrue → settle trail.
* **Logs** — runtime logs for your apps.
* **Observability** — per-app runtime metrics, served from Aomi's monitoring,
  with links into the relevant dashboards.

<Note>
  Two honest limits. The billing **statement** view can show clearly-flagged
  example data while the backend statement API catches up to the design. And
  most of **Settings** is staged, not live: billing setup happens on
  [chat.aomi.dev](https://chat.aomi.dev) settings, and per-project secrets
  live in the project's Environment tab, not in Settings.
</Note>

## Web or CLI?

Both drive the same lifecycle. Pick by task:

| Task                                            | Use                                                            |
| ----------------------------------------------- | -------------------------------------------------------------- |
| First app, no local toolchain                   | Platform — the New app wizard                                  |
| Deploy an existing repo you already own         | [CLI](/build/toolchain/aomi-build) — `aomi-build connect`, then either surface |
| Redeploy after a push                           | Either — one button here, `aomi-build deploy` there            |
| SDK bump on a connected project                 | Platform (PR flow) or `aomi-build sdk fix`                     |
| Secrets, provider keys, bots, usage, logs, metrics | Platform                                                    |
| Scripted or CI-driven deploys                   | CLI                                                            |

The CLI itself signs in through the platform: `aomi-build` opens
build.aomi.dev in your browser, you authorize once, and the deploy continues
in your terminal.
